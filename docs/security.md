# Security

## Secrets and config
- All secrets come from environment variables, validated by Zod at boot.
- `.env` is gitignored. `.env.example` lists every variable with fake values.
- Never log secrets, tokens, passwords, cookies, or authorization headers.
- Different secrets per environment.

## HTTP hardening
- **Helmet** enabled with defaults, reviewed per environment.
- **CORS**: allow only origins listed in `CORS_ALLOWED_ORIGINS` (comma-separated). Credentials allowed only if cookie auth is chosen. Never use `*` with credentials.
- **Body limits**: JSON 100kb default, configurable. Larger uploads go through a dedicated upload route later.
- `x-powered-by` disabled.
- `trust proxy` set through env when running behind nginx or a load balancer.

## Logging
- Pino with a request ID on every line.
- Redaction paths include `req.headers.authorization`, `req.headers.cookie`, `res.headers["set-cookie"]`, and any `password`/`token` fields.
- Do not log request bodies by default.

## Sentry
- DSN from env. Disabled if not set.
- `beforeSend` strips headers, cookies, request bodies, and user emails/IPs.
- `sendDefaultPii` is false.

## Error responses
- Production responses never include stack traces or internal messages for unexpected errors. Return a generic message plus a request ID.

## Validation
- Every request body, query, and path param is validated with Zod before reaching a controller.
- Reject unknown fields on write endpoints where practical (`.strict()`).

## Authentication and authorization (Phase 2)
Browser sessions use 15-minute signed access tokens and 30-day opaque refresh tokens. Only SHA-256 hashes of refresh and reset tokens are stored. Refresh reuse revokes its token family. Passwords use Argon2id. Access and refresh cookies are `HttpOnly`, `SameSite=Lax`, path-scoped, and `Secure` in production. Unsafe requests require a signed double-submit CSRF token. CORS credentials are restricted to exact configured origins. Authentication routes use Redis-backed rate limits; registration and reset responses do not disclose whether an account exists. Public registration grants only the customer role. Store ownership checks are added with vendor/store modules.

Password reset delivery is a port with no provider configured. Reset requests are stored as hashed tokens but cannot complete through normal use until an approved delivery adapter is added.

Vendor applications collect only business name, proposed store name, an optional description, and an E.164 contact phone in Phase 3. They do not collect business registration numbers, identity documents, financial data, or addresses. Applicants can read only their own history; reviewers require the admin role. Store updates are scoped to the authenticated owner, public reads expose active stores only, and contact phones are not included in public store responses. Admin role bootstrap is an operator-run CLI action against an existing account, never a public route.

## Payments (Phase 8)
- Payment references are generated by the server. Amount, currency, and account email come from persisted order/account data.
- Verify transaction status, reference, amount, and currency with Paystack before changing order state; never accept a browser redirect or webhook body as proof of payment.
- Verify webhook HMAC-SHA512 against the raw request bytes with constant-time comparison. Persist only event metadata and a SHA-256 payload hash, and deduplicate by event key.
- Payment attempts and refunds are idempotent. Active attempts are exclusive per order, and cumulative refunds cannot exceed the captured amount.
- A late payment for a cancelled order is recorded for admin attention; it never reopens the order or restores already released stock.
- `PAYSTACK_SECRET_KEY` is optional at boot so non-payment endpoints remain available, but payment routes fail closed with `503` when unset. It must be stored as an environment secret and never logged.

## Commissions and payouts (Phase 9)
- Commission rules and payout administration require the admin role; earnings, ledger, and payout creation use the authenticated vendor's owned store.
- Commission rules cannot be backdated or overlap at the same scope. Their rates are bounded to 0–100% and are applied with integer minor-unit arithmetic.
- Ledger entries are append-only and source-keyed for idempotency. Refund reversals are created only after a provider-confirmed successful refund.
- Payout requests reserve available balance in a serializable transaction. Paid state requires an admin and an external transfer reference; the server does not initiate external bank transfers or store bank account details.

## Rate limiting
Redis-backed limiter introduced in Phase 2, applied globally with stricter limits on sensitive routes.

## Dependencies
- `npm audit` in CI. Lockfile committed. Review any new dependency.

## Data protection
- Collect only the personal data needed. Plan for data export and deletion requests.
- Backups encrypted, with a tested restore process (Phase 12).

## Uploads (Phase 4)
- Validate type and size, store outside the app server (object storage), never serve user files from the app origin.
- Phase 4 stores product-media object metadata only. Upload routes are deferred until an object-storage provider is explicitly authorized; do not add local filesystem uploads.

## Inventory (Phase 5)
- Vendor inventory queries and writes are scoped to the authenticated owner's active store.
- Customers can reserve only active variants in active products and stores. Reservation ownership comes from the authenticated identity; request bodies cannot choose a user ID.
- Reservation release is scoped to both reservation ID and owner ID. Admin low-stock responses include store/product/variant details but no customer data.
- Serializable transactions with bounded retries prevent concurrent reservation requests from overselling. Holds expire after 15 minutes and cease reducing availability at expiration even before status cleanup runs.
- Inventory mutation routes are CSRF-protected and rate-limited. Public browse endpoints do not disclose exact stock counts.

## Cart (Phase 6)
- Cart reads and writes always scope through the authenticated user. Callers cannot choose a user/cart owner or submit a price.
- Cart mutation routes require CSRF and rate limits. Add/update uses the database variant price and verifies active listing state and current availability.
- Cart data includes only product/store data needed to render the buyer's own cart. A cart is not a stock reservation; checkout must revalidate price and inventory.

## Checkout and orders (Phase 7)
- Checkout accepts a strict address and cart confirmation only. It ignores client totals and recomputes every price and subtotal from PostgreSQL.
- `Idempotency-Key` is bound to the authenticated user and a hash of normalized checkout input to prevent duplicate orders and detect mismatched key reuse.
- Checkout, inventory allocation, reservation conversion, order snapshots, and cart clear are one serializable transaction. Cancellation can restore stock only from `pending_payment` and updates order/sub-order state atomically.
- Customer order reads are owner-scoped. Vendor reads scope through the owned store and omit address and customer identity.
- Shipping address is personal data stored only on the order and visible to its customer. Vendor disclosure is deferred until a later payment-confirmed phase.
