# Database Design

PostgreSQL accessed only through Prisma. **Prisma Migrate is the only migration system.**

## Conventions
- Models are `PascalCase` singular (`Product`). Tables are `snake_case` plural via `@@map("products")`. Fields use `camelCase` mapped with `@map` to `snake_case` columns.
- Primary key: string `id` (CUID2 or UUID), generated by the application or database, never sequential integers exposed to clients.
- Every table has `createdAt` and `updatedAt`.
- Soft delete (`deletedAt`) only where history matters (users, stores, products). Hard delete elsewhere.
- Money: `Int` (or `BigInt` if needed) in minor units, plus `currency` where relevant.
- Enums for fixed state sets (order status, store status).
- Foreign keys always declared. Choose `onDelete` deliberately (default `Restrict`).
- Index every foreign key and every field used in frequent filters or sorts. Unique constraints for slugs, emails, SKUs.
- Store timestamps in UTC.

## Migrations
- Create locally with `npx prisma migrate dev --name <short_description>`.
- Commit the generated migration folders.
- Production applies migrations with `npx prisma migrate deploy` only.
- Never edit a migration that has been applied anywhere shared. Add a new one.
- Destructive changes (drop column/table) use the expand and contract approach over two releases.
- Never run `migrate reset` against any shared or production database.

## Phase 1
Phase 1 contained only the PostgreSQL datasource and Prisma Client generator. Phase 2 adds `User`, `Role`, `UserRole`, `RefreshSession`, and `PasswordResetToken`. Phase 3 adds `VendorApplication` and `Store`; later business models remain out of the schema until their phase. With Prisma 7, the database URL and migration path are configured in root `prisma.config.ts`.

`VendorApplication.openUserId` is a nullable unique key set to the applicant ID only while an application is pending. Review clears it, preserving historical applications while the database enforces at most one pending application per user. `Store.ownerId` and `Store.slug` are unique. Application approval, vendor role assignment, and pending store creation run in one transaction.

Phase 4 adds `Category`, `Product`, `ProductVariant`, and `ProductMedia`. Categories use a self-relation for hierarchy and an implicit many-to-many relation to products. Product slugs are unique per store; SKUs are unique per store. A composite product/store key on variants prevents assigning a variant to a product from another store. `priceAmount` is an integer minor-unit amount and currency defaults to `NGN`. Product status and `deletedAt` support archival without deleting order-relevant catalog history. Product media stores object metadata only; no upload provider is configured.

Phase 5 adds `InventoryItem` and `StockReservation`. Every variant has one inventory record, created with the variant and backfilled at migration time. Database checks prevent negative on-hand/threshold values and nonpositive reservation quantities. Reservation availability is derived from active, unexpired reservation rows rather than a denormalized reserved counter. Stock reservation and stock edit transactions run at PostgreSQL serializable isolation and retry serialization conflicts a bounded number of times.

Phase 6 adds `Cart` and `CartItem`. A unique `Cart.userId` enforces one persistent cart per user; a unique `(cartId, variantId)` prevents duplicate variant rows. Cart item quantities and quoted prices are stored as integers and guarded by database checks. Cart reads join current variant/product/store data and active inventory reservations so current-price totals and availability remain authoritative. Cart quantities are not inventory holds.

Phase 7 adds `Order`, `SubOrder`, and `OrderItem`. Orders have a unique `(userId, idempotencyKey)` and a SHA-256 request hash. One order may have one sub-order per store. Item rows preserve product name/slug, SKU, variant options, unit price, quantity, and line total; variant deletion nulls the reference but leaves the snapshot. Order totals use `BigInt`; line and shipping-address invariants are checked by PostgreSQL constraints. Checkout and pending-payment cancellation run serializable transactions. `StockReservationStatus.converted` records holds consumed by checkout.

Phase 8 adds one `Payment` per order, multiple `PaymentAttempt` rows for retry history, deduplicated `PaymentWebhookEvent` metadata, and `Refund` records. Provider references and transaction IDs are unique. Refunds retain the initiating admin when available; system-created late-payment attention records have no initiating user. Webhook payloads are not stored, only their SHA-256 hash. Payment success and order/sub-order transitions commit in a serializable transaction; refund totals include pending and attention states when reserving the refundable balance.

Phase 9 adds effective-dated `CommissionRule` records, append-only `LedgerEntry` records, and `Payout` requests. Order items snapshot category IDs at checkout so later catalog edits do not change commission-rule selection. Ledger source keys prevent duplicate sale, commission, refund-adjustment, and payout entries. Payout requests reserve available ledger balance while requested or approved; marking a payout paid inserts its debit in the same serializable transaction as the state transition.

## Connections
- One shared Prisma client instance per process.
- Connect at startup, disconnect on shutdown.
- Connection pool size set through the `DATABASE_URL` or env config and tuned per environment.

## Transactions
Use Prisma transactions for any operation that writes more than one row that must succeed together (order creation, stock reservation, ledger entries).

## Seeding
Seed scripts live in `prisma/seed.ts`, are idempotent, and never contain real credentials.
